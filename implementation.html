      〇、白話版：這套東西到底在幹嘛

      用一個每天都在發生的例子講完整個方法：檢查便當店出餐流程。

      便當店有一條規矩：「接了單就一定要有出餐記錄，不能憑空消失。」過去這條規矩只存在老闆腦子裡，新人做錯了才被罵。這套方法就是把這種「腦子裡的規矩」變成機器會自動檢查的東西，分四步：

      1. 寫下規矩（Frozen Requirement）：把「接了單一定要有出餐記錄」白紙黑字寫下來，老闆簽名認可。這份文件之後不能再隨便改，不然檢查的標準本身在動。
      2. 做一個迷你廚房（Model）：不是真的廚房，是一個可以在電腦裡演練的小模型——只有三種狀態：接單、製作中、已出餐。
      3. 請奧客來亂搞一萬次（State Exploration）：讓 checker 在迷你廚房裡亂玩——接單不出餐、出餐完又退單、兩個人同時改同一張單……玩一萬遍，每次檢查規矩有沒有被破壞。人腦想不到的怪招它會試出來。
      4. 回真廚房驗證（Replay）：奧客若在迷你廚房成功搞砸（例如「同時按退單和出餐，單就不見了」），要回真正的廚房照同樣步驟做一次，確認真的會出事——迷你廚房畢竟是簡化的，可能誤報。

      找到真的會搞砸的狀況 → 修流程 → 規矩文件和迷你廚房同步更新 → 留一個自動檢查防止以後再壞。整個手冊下面就是在講這四步怎麼在軟體專案裡做。

      術語對照表（看不懂時回來查）

      術語白話便當店比喻
      Requirement / Spec規矩本身，白紙黑字「接了單一定要有出餐記錄」
      Invariant規矩的檢查公式，跑起來會回 true/false檢查員手上的打分表
      Model真實程式的迷你版，可以讓機器亂玩迷你廚房
      State / Transition訂單現在在哪個狀態／怎麼跳過去接單→製作中→已出餐
      State Exploration把所有可能操作順序都試一遍奧客亂搞一萬次
      Counterexamplechecker 找到的一組會搞砸的操作順序「先退單再出餐，單就消失」
      Replay把搞砸步驟拿到真實程式重做一次回真廚房照做一遍
      Witness證明檢查有真的走到重要情境，不是空跑確認演練中真的有出過餐
      Mutation故意把好東西弄壞，看檢查員會不會發現拔掉瓦斯看檢查員叫不叫
      Vacuous truth檢查看起來全過，但其實根本沒驗到「所有出餐都合格」但根本沒出過餐
      讀法建議：時間不夠就看這節 + 各節開頭的白話句；要動手才細讀步驟內容。

      一、核心原則：Generator ≠ Judge

      白話：出考卷的人不能自己改考卷——寫程式的和判對錯的要是兩套東西。

      整個方法論可以壓縮成一條規則：

      產生答案的系統，不能同時是判定答案正確的系統。

      因此 Factory 實際上是兩條彼此獨立的 pipeline：

                    Human Intent
                   │
                   ▼
           Frozen Requirement
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
   CODE PIPELINE         FORMAL PIPELINE
        │                     │
    Red Test              Invariants
        │                     │
   Implementation         Human Approval
        │                     │
   Integration              ▼
        │                As-Is Model
        │                     │
        │              State Exploration
        │                     │
        │               Counterexample
        │                     │
        └──────────┬──────────┘
                   ▼
            Real-world Replay
                   │
                   ▼
              Fix / Reject
                   │
                   ▼
            Re-verification

      Formal pipeline 不是 CI 裡多掛一個步驟，它是 Factory 的第二套 correctness engine。AI 可以產生 implementation，但「什麼叫正確」由另一套 executable specification 決定。

      二、Step 0 — 選擇值得建模的目標

      白話：不是所有東西都值得這樣搞。挑「規矩多、出錯很貴、人腦容易漏」的地方——狀態機、錢、庫存這種。

      不是所有程式都值得建 formal model。先過這張篩選表，符合越多越值得做：

      類型特徵例子
      State Machine有明確狀態與轉換規則訂單、工單、審批、付款、出貨流程
      Concurrency多個 transaction 可交錯執行雙人同時修改、扣庫存競爭、optimistic lock、重複付款
      Distributed Workflow跨服務、非同步、會重試Saga、Outbox、event-driven、idempotency
      Authorization誰能做什麼轉換有規則approve / rollback / 越權操作
      Resource Invariant有可計算的守恆條件庫存 ≥ 0、借貸平衡、容量上限、資源不得雙重持有

      反過來，CRUD 頁面、報表排版、UI 外觀這類「沒有可寫成 predicate 的規則」的東西，不適合。

      判斷標準：如果你能把需求寫成「∀ state：某條件必須成立」，就值得建模。

      三、Step 1 — Frozen Requirement：只從需求寫規格

      白話：規矩要照「應該怎樣」寫，不能照「程式現在怎樣」寫——不然 bug 會被你寫進規矩裡當成對的。

      這是最容易被跳過、也最重要的一步。把業務規則先固定成編號條文（R1、R2 … Rn），寫進一份獨立的規格檔（例如 source.md）。

      此階段的硬性紀律：

      只看需求
不看 production behavior
不建立 as-is model
不修改 src/

      原因：如果照著 implementation 寫 specification，implementation 的 defect 會被一起定義成「正確」，verification 就永遠找不到它。

      正確：Requirement → Invariant
錯誤：Production → Model → Invariant  ← 兩邊一起複製 bug

      語意裁定清單

      寫規格時一定會撞到模糊地帶。Agent 不要自行推測，把每個 ambiguity 列成問題，由人裁定後記錄進規格。案例中實際被裁定的例子：

      • createOrder 是否一律產生 NEW？
      • PENDING → PENDING 算不算合法 transition？（裁定：same-state write 不允許）
      • stale read 的定義是什麼？（裁定：嚴格解讀 fresh read）
      • 失敗的 transaction 算不算 committed history？（裁定：不算）
      人類在這裡的工作不是 review code，是決定世界的規則。

      實戰教訓：命名會說謊，語意要從「程式如何使用」驗證，不能只看標籤。某 ERP 的訂單狀態欄位值 3 在資料表叫「取消」，但程式把它和值 2 一起視為「已結案」、UI 是「結案／取消結案」toggle——它實際是「手動結案」。若照名字把 3 寫成「取消且為終態」的規格，會砍掉一個真實存在的重開功能。裁定模糊地帶前，先查程式如何消費這個值。

      四、Step 2 — Invariant Registry：把規則變成可計算的 predicate

      白話：把「借貸要相等」這種句子翻譯成電腦算得出 true/false 的式子，一條規矩對應一個式子。

      自然語言「已送達訂單不得取消」必須變成 machine-checkable property：

      ∀ transition:
  previous == DELIVERED
      ⇒
  next != CANCELLED

      實作建議：

      • 每條 invariant 用固定命名（INV_xxx），一條對應需求裡的一條 R
      • invariant 檔（如 invariants.qnt）獨立於 model 檔，分開版控
      • Invariant 要經過 Human Approval 才進入檢查流程——它是 authority，不是 artifact

      案例中的 invariant 清單可當模板參考：

      INV_newOrderStartsNew
INV_normalFlowIsSingleStep
INV_cancelOnlyFromNewOrPending
INV_errorOnlyFromAllowed
INV_onlyPermittedTransitions
INV_committedWritesAreSequentialAndFresh

      五、Step 3 — As-Is Model：投影 production，不是寫理想模型

      白話：迷你廚房要照真廚房現在的樣子蓋（包括它原本的毛病），不是照你理想中的樣子——不然驗證的不是現實。

      Model 的本體論定位要分清：

      Requirement → Invariant  = Authority（世界應該如何）
Production → As-Is Model = Projection（程式實際如何）

      建模原則：

      • 照實際行為建模：程式沒有 lock，模型就不要有 lock。案例中 OrderEntity 沒有 @Version，模型就刻意保留無鎖行為來探索 stale read
      • 把 transaction 拆開：單一函式呼叫看不出併發問題，transaction 要建模成可交錯的步驟：
      Txn A: begin → read → （可被插入的空隙）→ commit
Txn B: begin → read → commit

於是可表達：
A.read NEW ── B.read NEW ── A.commit DELIVERED ── B.commit CANCELLED
      • 建模的範圍是行為（action 與它對狀態的影響），不是逐行翻譯程式碼

      六、Step 4 — State Exploration：讓 checker 當 systematic adversary

      白話：checker 的工作就是想辦法搞砸。它把所有操作順序排列組合亂試，專挑人想不到的怪順序。

      不要自己寫 testcase 列舉情境，讓工具在 state space 裡走 action sequence，每到一個 state 就檢查全部 invariant：

      Initial State
     │
 ┌───┼───────────┐
 ▼   ▼           ▼
 A   B           C     ← 每個分支檢查 R1…Rn 是否仍成立

      與 fuzz testing 的差別：它操作的是抽象狀態機 + 正式 property，不是隨機 API input，所以能找到「transaction interleaving」這類單元測試幾乎寫不出來的路徑。

      工具的誠實定位

      案例中實際跑的是 quint run --max-samples=10000——這是 sampling / simulation，不是無界狀態空間的數學證明。要更強的保證才用 quint verify（symbolic model checking；inductive invariant 可提供更完整結果）。

      對外溝通時講精確：「Formal Specification + Executable Model + Bounded/Sampled Exploration」，不要說「系統已被證明正確」。

      七、Step 5 — Counterexample → Production Replay（雙重驗證）

      白話：迷你廚房找到問題只能算「嫌疑」，要回真廚房照做一次確認真的會壞，才算數。

      Formal model 找出的東西是候選 defect，不是已定案 bug。模型可能有建模誤差，所以流程上多一道 replay：

      Formal Counterexample
        ↓
Candidate Defect（候選，未回放）
        ↓
Regression Reproduction（寫成真實測試）
        ↓
Production RED  ← 在真實程式上重現失敗
        ↓
Confirmed Defect
      • Counterexample trace 本身就是 bug reproduction recipe，直接存證、進 work item
      • 若 replay 不出來，回頭檢查的是 model 是否失真——這也是 model 品質的回饋
      • 案例實績：修復前模型 6 invariants × 3 instances = 18 checks，18/18 全數找到反例（非法建立、跳階、終態逃逸、stale-read 覆寫）

      八、Step 6 — 修復後重建模型，不把模型調綠

      白話：修好之後要重蓋迷你廚房再驗一次；絕對不能為了讓檢查過關而去改迷你廚房的規矩。

      修完 bug 之後不要改 model 改到 pass。舊模型描述的是修復前的系統，不是永恆的規格：

      重新讀 production code
        ↓
重新建立 as-is model
        ↓
重新執行 verification

      只有 Invariant 是 authority；Model 是 production 的投影，production 變了 model 就要重投影。把「修改 model 直到綠燈」當作流程上的 anti-pattern 明文禁止。

      九、Step 7 — Witness 與 Mutation：證明「全綠」不是空轉

      白話：檢查全過有兩種可能：真的沒問題，或檢查根本沒跑到重點。用兩招分辨——確認重要情境有被走到（witness）、故意弄壞看檢查會不會叫（mutation）。

      Witness — 防 vacuous truth

      「所有 DELIVERED 訂單都符合 X」在模型根本走不到 DELIVERED 時會 vacuously 成立。所以要為重要狀態定義 witness（「某件事確實發生過」）：

      witness: DELIVERED reached
witness: normal transition reached
witness: cancel reached
witness: concurrent scenario reached

      案例標準：10 個 witness 全部命中，最低一項 47 / 10000 traces。驗證品質 = bad state not found + important states actually reached。

      Mutation — 驗證 checker 有辨識力

      故意把已知正確的東西弄壞，看 checker 會不會變紅：

      Mutation預期結果
      拿掉 version checkR6（併發 invariant）FAIL
      拿掉 transition validationR5 FAIL
      createOrder 直接建 SHIPPEDR1 FAIL
      Correct system → GREEN、Known broken system → RED，兩者都成立才算 checker 有 sensitivity。

      反向紀律 — 修復後要砍掉空轉的檢查

      vacuous green 不只發生在「狀態走不到」，也發生在「規則被修掉了」。當某條 invariant 針對的缺口經裁定修復、該違規在模型中結構性地不可能再發生時，要連同它的追蹤狀態一起移除，而不是留著一個永遠綠的檢查假裝還在驗證。實戰例：「close() 對結案單有定義」這條 invariant 在裁定「冪等回傳」並實作後，觸發它的旗標成為永遠 false 的死狀態——整個機制刪除才是誠實的驗證。

      十、Formal Work Item 有自己的狀態機

      白話：驗證工作本身也要追蹤進度——規格草稿、模型建好、找到反例、修復完成，每一步都有狀態。

      形式化驗證工作本身也應該是一個被追蹤的 flow，而不是散落的 PR：

      DRAFT_REQUIREMENT
        ↓
SNAPSHOT
        ↓
INVARIANT_DRAFT
        ↓
HUMAN_SEMANTIC_REVIEW
        ↓
INVARIANT_APPROVED
        ↓
MODEL_BUILDING
        ↓
CHECKING
        ↓
 ┌──────┴────────┐
 ▼               ▼
PASS          COUNTEREXAMPLE
 │               │
 │               ▼
 │            REPLAY
 │               │
 │        ┌──────┴──────┐
 │        ▼             ▼
 │    CONFIRMED      REJECTED
 │        │
 │        ▼
 │       FIX
 │        │
 └────────┴──────┐
                 ▼
             REVERIFY
                 │
              WITNESS
                 │
              MUTATION
                 │
                 ▼
               CLOSED

      每個階段的產出物（spec 版本、invariant 檔、counterexample trace、replay 測試、witness/mutation 報告）都進 Evidence Store。

      十一、角色分工總表

      白話：誰負責什麼——AI 寫程式跑檢查、人類定規矩和裁定模糊地帶。

      角色職責可替換性
      HumanSemantic Authority：定義需求、裁定語意、批准 invariant不可被 AI 取代
      Formal SpecificationCorrectness Authority：什麼叫對人審後凍結
      AI AgentExecutor：產生 implementation、產生 model 草稿可替換（GPT / Claude / …）
      Model CheckerSystematic Adversary：在 state space 裡找破壞路徑可替換（Quint / TLA+ / Alloy）
      Regression / E2EReality Check：確認 abstract counterexample 是真實 bug—

      十二、落地 Checklist 與界線

      白話：照這個清單做就不會漏；以及先講清楚這套方法做不到什麼，免得期待落空。

      最小可行流程

      1. 選 1 個狀態機或 resource invariant 明確的 aggregate
      2. 寫 frozen requirement（R1…Rn），人裁定語意模糊處
      3. 寫 invariant 檔，人批准後凍結
      4. 建 as-is model（含 transaction interleaving）
      5. 跑 sampling（quint run），收 counterexample
      6. 每個 counterexample 寫成真實 replay 測試，確認 RED
      7. 修 → 重建 model → re-verify → witness + mutation
      8. 全部產出物進 Evidence

      要講清楚的界線

      • Sampling ≠ proof：quint run 是有界的狀態探索，發現能力強但不等於數學完備；需要更強保證時用 symbolic model checking / inductive invariant
      • Model ≠ production：model 是投影，會失真；所以 counterexample 必須 replay 才算數
      • 先小後大：案例也是先從 6 條 invariant、3 個 instance 開始，不要一開始建全系統模型
      一句話：AI 是可替換的執行器，Formal Specification 是正確性權威，Model Checker 是系統化的對手，Human 是語意權威——四者分離，才是 Software Factory。

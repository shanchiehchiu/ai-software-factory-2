      〇、三十秒讀完的故事

      重點先講：這個流程裡，人類真正要做的事只有一件——訂好規則。
      規則定完之後，寫規格、蓋模型、亂玩一萬次、找反例、回真實程式重現、修 bug、再驗證——全部由 AI agent 自己完成。這頁紀錄裡，人只出現三次，每次都是回答「業務上這樣對不對」的裁定題，其他一行 code 都沒碰。

      銷售訂單只有三個狀態：未結案、結案、還有一個叫「取消」。看起來簡單到不可能出錯。

      我們把「訂單可以怎麼跳狀態」寫成一份給機器看的規則書，然後讓一個叫 Quint 的模型檢查器在模擬環境裡亂玩一萬次——用盡各種人類想不到的操作順序去戳它。結果抓到兩個真 bug：

      1. 幽靈按鈕：對已結案的訂單再按一次「結案」，程式會踩到一個從未設定的變數——工程師手寫測試永遠不會想到要按第二下。
      2. 後門寫入：刪掉出貨單時，程式不走正常流程，直接偷改訂單狀態——連「手動關掉的單」也會被它偷偷打開。

      然後是最戲劇化的發現：那個叫「取消」的狀態，根本不是取消——程式其實把它當「手動結案」在用，名字從一開始就寫錯了。差點因為信錯名字，把一個正常功能當 bug 砍掉。

      修完之後，我們留了自動檢查守在程式碼裡，以後誰想繞道改訂單狀態，CI 直接擋下。下面是完整過程。

      一句話：讓機器用一萬種亂七八糟的方式使用你的系統，它會找到你永遠想不到的 bug。

      一、這份文件是什麼

      白話：這頁記錄了一次真實的「機器抓 bug」過程，從頭到尾跑完一輪。

      這是一場已經跑完的實戰紀錄：在一個真實的 Laravel ERP 上，照實作手冊的流程走完「選目標 → 寫規格 → 建模 → 亂玩找 bug → 回真實程式重現 → 修復 → 確認檢查沒空轉」的完整循環。

      第二節是主體，每個步驟都寫「這一步在幹嘛、為什麼、發生什麼」；第三節給想自己跑跑看的人留工具和指令；第四節把這套方法的界線講清楚。文中引用的檔案都是該 ERP 裡的實際程式碼。

      二、執行紀實 — 手把手走一遍

      白話：照著實際跑過的順序，一個步驟一個步驟帶你看——兩個真 bug、一次命名翻車、七次 commit。

      每一步都講三件事：在幹嘛、為什麼這樣做、實際發生了什麼。想對照方法論原文可以看實作手冊的 Step 0–7。

      Step 0 — 先決定拿什麼開刀

      別急著寫任何東西。值不值得這樣搞，先看五種體質：有狀態跳的（訂單、審批）、會被同時操作的（兩人搶同一筆資料）、跨服務會重試的、有權限規則的、有加減要能守恆的（借貸、庫存）。符合越多越值得；CRUD 頁、報表排版這種「錯的定義寫不出來」的，別浪費力氣。

      拿這張表對 ERP 掃過去，命中三個：訂單的狀態跳轉、傳票的借貸平衡、庫存的加減守恆。第一個挑 SalesOrder——缺口最集中，而且萬一改壞了波及範圍最小，適合拿來練手。

      Step 1 — 先把規矩白紙黑字寫下來

      還不能碰程式。先把「怎樣算對」寫成一份文件 fv/sales-order/source.md：三個狀態是什麼意思、哪些跳轉合法、模糊地帶列成問題等人裁定。照「應該怎樣」寫，不照「程式現在怎樣」寫——不然 bug 會被抄進規矩裡當成正確。

      這一步撞上教科書沒寫的坑：狀態名會說謊。值 3 在資料表叫「取消」，但程式其實把它當「手動結案」用（getCloseAttribute 把 2、3 都算已結案）。我們先照名字把它當「取消＝終態」裁定，差點砍掉一個正常功能；後來從程式實際用法發現是名字寫錯，用 migration 正名為「結案（未出貨）」。教訓：寫規矩前，先看程式怎麼「用」這個值，別信它「叫」什麼。

      Step 2 — 把規矩翻譯成機器判得動的檢查

      「狀態不能亂跳」這種話機器聽不懂，要變成能算對錯的檢查。規矩寫進模型檔 sales-order.qnt：一張「合法跳轉清單」{1→2, 1→3, 2→1, 3→1}，加兩條檢查——「狀態只能沿清單跳」「狀態只能是 1/2/3」。以後業務每裁定一次，清單就回填一次。

      「借貸要相等」這種金額守恆的規矩不用進模型——用 PHP 寫個裁判類（VoucherBalanceInvariant）更直接，放在 SummonService 的寫入咽喉點，所有傳票寫入都繞不過它。

      Step 3 — 用 Quint 蓋一個迷你版系統

      工具出場：Quint，一個模型檢查器（model checker）。你用它的語言把系統寫成一個「迷你版」，它就能在模擬環境裡把所有可能的操作順序排列組合著玩；一旦玩到犯規，會把整段過程一步步錄下來。

      重點：迷你版要照真實程式的壞習慣做，不能美化。close() 在真實程式是「先讀狀態、再寫回」兩步，模型就照樣拆兩步，這樣 Quint 才玩得動「A 讀到狀態時 B 已經改掉了」的穿插狀況；Controller 偷改狀態的後門也如實做進去，當作一個繞道動作。美化過的模型只會驗證到一個不存在的理想系統。

      Step 4 — 放手讓它亂玩一萬次

      前置作業完了，執行 quint run --max-samples=10000——讓機器用一萬種亂七八糟的順序操作迷你版。抓到兩個犯規：

      • 「只能沿合法清單跳」被打破 ❌ — 刪銷貨單時訂單狀態被繞道直寫回 1，連不該動的單也會被碰
      • 「每個狀態都要有定義」被打破 ❌ — 對已結案的訂單再按結案，程式踩進一個從沒定義過的分支

      兩段犯規過程的完整操作錄影存在 fv/sales-order/counterexamples/。這就是為什麼要用機器玩——人寫測試不會想到「對結案單再按一次結案」這種操作。

      Step 5 — 先別修，回真實程式重現一次

      機器說會壞，可能只是模型想錯了。所以把那兩段錄影拿回真實程式重播：寫成 PHPUnit 測試（SalesOrderStateMachineReplayTest），實際跑 OrderService 和 SalesSoldOrderController::destroy()。

      結果兩條都真的壞掉——不是模型誤報，是真 bug，可以修了。

      Step 6 — 修，但要修兩邊

      修 bug 不是只改程式：真實程式要改，規格和迷你版也要跟著改，不然下次驗證會拿舊規矩誤殺新行為。這次的修法：

      • 業務裁定：結案單再按結案＝當沒按，直接回傳原狀；status 3 正名為手動結案，3→1 是合法的「取消結案」切換
      • 程式：狀態回寫收進 Service 的 reopen()、Controller 兩處直寫刪掉、close() 補上結案狀態的處理
      • 迷你版：跟著真實程式改寫，合法跳轉清單回填裁定結果
      • 重驗：再亂玩一萬次，兩條檢查全綠

      Step 7 — 全綠了？先別收工

      綠燈有兩種：「真的檢查過沒問題」，和「檢查根本沒跑到」。要確認是前者，做三件事：

      • 目擊檢查：反問機器「你有真的走到結案嗎？有真的走到重開嗎？」三條探針命中率 72%／87%／97%——有走到，不是空轉
      • 故意搞破壞：塞個假繞道檔案進 app/，看「只有 Service 能改狀態」的檢查會不會抓——會，還正確報出檔名
      • 反過來也要刪：修好後有條檢查已經「結構上不可能再犯規」，留著只會製造假綠燈——刪掉

      這趟學到的三件事

      • 狀態名會說謊：寫規格前先查「程式怎麼用這個值」，別信資料表標籤。
      • 修復是雙向的：code 修好了，規則書也要回填（2→1 從「違規」變「合法」），不然檢查會誤殺新行為。
      • 檢查也會過期：不再可能觸發的檢查要刪，全綠的清單應該每條都有活的意義。

      最後的狀態機長這樣

      目前狀態動作結果
      1 未結案結案，無銷貨單→ 3 結案（未出貨）
      1 未結案結案，有銷貨單→ 2 結案
      2 結案再按結案沒反應，不寫入（按幾次都一樣）
      2 結案刪除銷貨單→ 1 未結案（經 reopen()）
      3 結案（未出貨）取消結案→ 1 未結案（重開）
      3 結案（未出貨）刪除銷貨單不動（reopen 只管 2→1）

      三、想自己跑看看

      白話：工具安裝與指令速查，照抄就能跑。

      裝 Quint

      npm install -g @informalsystems/quint

      檔案放哪

      建議直接開在專案 repo 裡（這個 ERP 放在 fv/）：

      fv/
└── sales-order/
    ├── source.md          ← 白紙黑字的規矩（Step 1 產出）
    ├── sales-order.qnt    ← 規矩 + 迷你版系統（Step 2、3 產出）
    └── counterexamples/   ← 每次抓到的犯規錄影存證

      怎麼跑

      # 主力用法：抽樣亂玩
quint run fv/sales-order/sales-order.qnt \
  --main=salesOrder \
  --invariant=inv_onlyLegalTransitions \
  --max-samples=10000

# 目擊檢查：確認重要狀態真的有被走到（防空轉）
quint run fv/sales-order/sales-order.qnt \
  --main=salesOrder \
  --witnesses=witness_closedReached \
  --max-samples=10000

      抓到犯規時，輸出的操作錄影就是 bug 的重現步驟——拿去寫成 PHPUnit 測試重播。

      四、先講好：這套方法保證什麼、不保證什麼

      白話：不是萬靈丹——哪裡有用、哪裡沒用，先說清楚。

      • 「亂玩一萬次沒抓到」≠ 證明正確：它找 bug 很強，但抽樣就是抽樣，不是數學證明。要更強的保證得用更重的工具（quint verify）。
      • 規矩由人定：「結案單按結案該怎樣」是業務決定，機器不會替你答——它只負責在你定了規矩之後，確認程式有沒有遵守。
      • 只保證你寫出來的規矩：借貸相等擋不住「科目掛錯」「金額算錯」——規矩沒寫到的錯，檢查不會抓。
      • 歷史資料不受保護：檢查只擋新的寫入，資料庫裡已經存在的錯不會自己好。
      最小第一步其實不用裝任何工具：先把「借貸要相等」抽成一個裁判類放進寫入咽喉點——今天就做得到。

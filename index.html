    目錄

      一、核心結論

      AI 正在把「寫程式」快速商品化。

      當 AI 可以大量產生 code、test、文件、migration、API、UI，Software Factory 真正的瓶頸就不再是：

      誰能寫得更快？

      而會變成：

      我們如何知道 AI 產生的東西真的正確？

      因此 AI Software Factory 的下一階段，不應只是增加更多 Agent，而是把軟體工程逐步轉成：

      Specification → Generation → Verification → Evidence → Release

      也就是從：

      Agentic Software Engineering

      進一步走向：

      Verifiable Software Engineering

      Martin Kleppmann 在 2025 年提出的核心判斷正是如此：Formal Verification 過去無法普及，主要不是因為它沒有價值，而是因為建立 formal proof 的人工成本太高；如果 LLM 能大量自動產生 proof，而 deterministic proof checker 負責判斷證明是否成立，Formal Verification 的經濟結構就可能徹底改變。

      五、但 Multi-Agent 並沒有真正解決 correctness

      Agent A 寫程式

      Probabilistic Generator

      但仍然沒有得到：

      Correctness Guarantee

      Agent 甚至可能共同接受同一個錯誤假設。

      六、真正需要的是 Deterministic Verification Layer

      AI Software Factory 最重要的架構變化可能是：

                AI
           ↓
     Generate Artifact
           ↓
┌──────────────────────┐
│ Deterministic Checker │
└──────────────────────┘
           ↓
      Pass / Fail

      也就是：

      AI 負責搜尋解法。

      而：

      Machine 負責判定解法是否成立。

      這兩件事情必須分開。

      七、這就是 Formal Verification 開始重要的原因

      Formal Verification 的基本形式是：

      Specification
      +
Implementation
      +
Proof
      ↓
Proof Checker
      ↓
Valid / Invalid

      例如要求一個函式：

      withdraw(balance, amount)

      必須滿足：

      amount <= balance

且

new_balance = balance - amount

且

new_balance >= 0

      AI 可以產生：

      Implementation
+
Proof

      但是 AI 沒有最終決定權。

      最後由：

      Lean
Isabelle
Coq / Rocq
Dafny
F*
Verus
SPARK
SMT Solver
Model Checker

      進行判定。

      Kleppmann 特別指出，proof generation 是 LLM 很適合的一種工作，因為 AI 即使 hallucinate，錯誤 proof 也無法欺騙正常運作的 proof checker；失敗後 Agent 可以重新搜尋新的證明。

      十、最重要的不是 Code，而是 Contract

      Human Intent

      而不是：

      換句話說：

      Code 會逐漸變成 Spec 的 compiled artifact。

      就像今天工程師通常不需要閱讀 compiler 產生的 machine code。

      未來某些 AI-generated code 也可能不再需要人類逐行閱讀。

      真正需要 review 的會變成：

      Requirement
Specification
Invariant

      Kleppmann 甚至直接提出類似的想像：如果 AI 能產生 implementation 與 correctness proof，人類可能不再需要把 AI-generated source code 本身當成主要 review 對象。

      十一、真正的新瓶頸：Specification

      但 Formal Verification 並不代表：

      Verified = 正確產品

      它真正代表的是：

      Implementation
符合
Specification

      因此：

      錯誤 Specification
+
完美 Implementation
+
完美 Proof
=
完美證明一個錯誤需求

      所以 Software Engineering 的難題會往上移。

      以前的問題是：

      你程式有沒有寫錯？

      未來會逐漸變成：

      你 Spec 有沒有寫錯？

      這也是目前 formal-AI 研究非常重要的方向。

      例如 2026 年的 Verus-SpecGym 就專門研究：

      AI 是否能把 informal requirement 正確轉換成 formal specification。

      研究本身直接指出：即使 implementation 有 machine-checked proof，也無法保證 formal spec 本身符合原始使用者意圖。

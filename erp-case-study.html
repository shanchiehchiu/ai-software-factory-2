    目錄

      一、這份文件是什麼

      主文講「為什麼要分級驗證」，實作手冊講「通用流程怎麼走」。這份文件只回答一件事：

      在這個 Laravel ERP 裡，第一步到底動哪幾個檔案、寫什麼東西、跑什麼指令。

      所有引用的檔案與行號都是該 ERP 裡的實際程式碼。

      二、現況盤點：三個可以立刻下手的缺口

      缺口位置現況
      單據狀態機沒有規格app/Service/Sales/OrderService.php:325 等 20+ 處 close()狀態是 statuses_id 魔法數字，轉換規則散在各 Service，部分轉換根本沒定義
      借貸平衡檢查散落SummonController、VoucherTransferController:666同一條「借貸必須相等」有至少三份各自實作的 array_sum 比對
      庫存彙總表有繞道寫入StockQuantityService 之外的 ~17 個檔案直接碰 product_stocks原子異動服務本身寫得好，但「只能經由它寫」沒有任何機制保證

      三、目標一：銷售訂單狀態機（第一個建模對象）

      為什麼先選它

      狀態少（只有 3 個）、轉換已經出 bug、且「刪除銷貨單會回寫訂單狀態」這種繞道轉換正是 model checker 擅長抓的東西。

      從程式碼讀出的 As-Is 轉換表

      狀態定義在 2024_02_02_164215_create_sales_order_statuses_table.php：

      1 = 未結案
2 = 結案
3 = 取消

      實際程式裡存在的轉換：

      轉換觸發位置備註
      1 → 3（未結案→取消）OrderService::close() :327無 sold_order 時
      1 → 2（未結案→結案）OrderService::close() :336已有關聯銷貨單時
      3 → 1（取消→未結案）OrderService::close() :331取消的單可以復活
      * → 1（任何→未結案）SalesSoldOrderController :1822, :1835刪除銷貨單時繞過 OrderService 直接改狀態
      2 → ?（結案→?）OrderService::close() :339未定義：$updateData 沒賦值就 update()

      注意最後兩列——這不是假設的風險，是已經存在的兩個 defect：結案單再按「結案」會對未定義變數做 update；而結案狀態可以被另一個 Controller 的刪除流程悄悄改回未結案。

      需要人裁定的問題（Spec 寫不出來的地方）

      1. 已結案（2）的訂單再按「結案/取消」按鈕，應該：報錯？無視？還是允許重新開啟？
      2. 取消（3）→ 未結案（1）這條復活路徑是業務需求還是意外？
      3. 刪除銷貨單把訂單改回未結案，是設計還是 bug？（若是設計，要寫進規格；若是 bug，model 會立刻抓到）
      4. 「結案」和「取消」的業務差異是什麼？結案是否意味著不可再異動關聯單據？

      Invariant 草稿（人裁定後再凍結）

      INV_onlyLegalTransitions
  只允許：(1→3) (1→2) (3→1) 以及裁定後的其他轉換
  禁止：  2→任何狀態、3→2、2→3 …

INV_closeRequiresDefinition
  對任何 status ∈ {1,2,3}，close() 的結果必須有定義
  （目前 status=2 會踩未定義變數 —— 已知的反例）

INV_reopenOnlyViaDefinedPath
  狀態回到「未結案」只能經過規格定義的路徑，
  不允許 Controller 繞過 Service 直接 update statuses_id

      Model 要建模的東西

      • 單一訂單的狀態 + 是否有關聯 sold_order
      • action：close()、deleteSoldOrder()（繞道寫入！）
      • transaction 拆 begin/read/commit，才能跑出「兩人同時按結案」的交錯

      四、目標二：借貸平衡（最容易寫成 executable contract）

      現況

      「Σ借 = Σ貸」目前有三份實作，散在不同 Controller：

      SummonController :298, :530
  round(Σdebit) - round(Σlender) != 0 → throw

VoucherTransferController :666
  同樣邏輯再寫一份

      而真正的產生者 VoucherTransferService（1956 行）裡有「依目標未稅整數分配四捨五入差額，避免借貸差 1」的邏輯（:1491）——這代表 invariant 其實存在，只是沒有被抽成一個可被任何傳票產出共用的裁判。

      落地做法

      1. 抽一個 app/Service/Finance/VoucherBalanceInvariant.php：輸入分錄陣列，輸出 pass/fail + 差額
      2. 三處 Controller 檢查全部改呼叫它（消掉重複實作）
      3. 寫 property test：對 VoucherTransferService 餵隨機合法單據組合，每次產生的傳票都必須過 invariant
      // tests/Unit/Finance/VoucherBalanceInvariantTest.php 概念稿
public function test_generated_voucher_always_balanced(): void
{
    // 對各種單據型態（Payment / Receipt / RestockOrder ...）
    // 產生 voucher entries，斷言 Σdebit == Σlender
}

      這是最便宜的一刀：不用裝 Quint、不用建模，就把一條散落規則變成 executable contract。

      落地做法：兩條 invariant

      INV_singleWriterPath（架構測試）
  斷言：product_stocks 的寫入只能出現在 Stock/ 目錄的允許清單內
  做法：一個 PHPUnit 測試 grep app/ 裡所有 product_stocks 寫入，
       不在白名單就 fail —— 把「慣例」變成 CI 會擋的規則

INV_stockConservation（稽核回放）
  斷言：stock(product, depot) == Σ 所有合法異動記錄
  做法：對有異動流水檔的品項做 replay 對帳測試

      注意：有些列出的檔案可能只是「讀」product_stocks，落地前先逐一確認是讀是寫——白名單判斷本身就是一次架構盤點。

      六、Quint 怎麼裝、放哪、跑什麼

      安裝

      npm install -g @informalsystems/quint

      建議的檔案位置（開在 ERP repo 內）

      fv/
├── sales-order/
│   ├── source.md          ← Frozen Requirement（R1…Rn + 語意裁定紀錄）
│   ├── invariants.qnt     ← 只從需求寫，人審後凍結
│   ├── model.qnt          ← As-Is Model（照 production 實際行為投影）
│   └── counterexamples/   ← 每次發現的 trace 存證
└── voucher/
    ├── source.md
    ├── invariants.qnt
    └── model.qnt

      執行

      # 抽樣探索（sampling，主力用法）
quint run fv/sales-order/model.qnt \
  --invariant=inv_onlyLegalTransitions \
  --max-samples=10000

# witness：確認重要狀態真的有被走到（防空轉）
quint run fv/sales-order/model.qnt \
  --invariant=witness_closedReached --max-samples=10000

# 需要更強保證時才用 symbolic model checking
quint verify fv/sales-order/model.qnt --invariant=...

      產出的 counterexample trace 就是 bug reproduction recipe，拿去寫 PHPUnit replay 測試。

      七、Counterexample → Replay 在這個專案長什麼樣

      假設 Quint 對「兩個併發 close()」吐出反例：

      State 0: order.status = 1
TxnA: read status=1, sold_order exists → 打算寫 2
TxnB: read status=1, sold_order exists → 打算寫 2
兩個都 commit → 表面沒壞，但若是 1→3 與 1→2 交錯就出事

      Replay 測試寫在 tests/Feature/，用兩個 DB connection 模擬交錯：

      // tests/Feature/SalesOrderConcurrentCloseTest.php 概念稿
public function test_concurrent_close_does_not_produce_illegal_transition(): void
{
    // 兩個 PDO connection 各自開 transaction，
    // 交錯執行 OrderService::close() 的 read / update，
    // 斷言最終狀態 ∈ 合法集合且只發生一次轉換
}

      規則：model 抓到的叫「候選 defect」，replay 在真實 Laravel 跑出 RED 才算確認；replay 不出來就回頭修 model——model 是投影，會失真。

      八、落地順序與產出物

      順序工作產出物對應層級
      1抽 VoucherBalanceInvariant、消重、寫 property test1 個 Service + 1 個測試檔L3
      2寫「product_stocks 只能經白名單寫入」架構測試1 個測試檔 + 白名單清單L3
      3SalesOrder：frozen requirement（先裁定第 3 節那 4 個問題）fv/sales-order/source.mdSpec
      4invariants.qnt + model.qnt + quint runqnt 檔 + counterexample 存證L3.5
      5每個 counterexample 寫 replay 測試、修 bug、重建 modelRED→GREEN 測試 + 新 model閉環
      6witness + mutation 檢查，證明 checker 有空轉防呆與辨識力驗證報告品質保證

      前兩項不碰 Quint，純 PHP 就能做，先建立「規則可以被機器執行」的肌肉；第 3 項開始才進 formal pipeline。

      九、要事先講清楚的界線

      • PHP 沒有 proof checker：這裡做的是「Executable Spec + Sampled State Exploration」，對應主文的 L3~L4，不是 L5 數學證明
      • quint run 是 sampling：找 bug 很強，但「沒找到」≠ 證明正確；要更強才上 quint verify
      • 規格由人定義：第 3 節那 4 個問題 AI 不能代答——「已結案單按鈕該怎樣」是業務決定
      • 金額是 float：number_format($delta, 4) 的精度語義要寫進 spec，不然 invariant 本身會有歧義
      最小第一步：不用裝任何新工具。先把 VoucherBalanceInvariant 抽出來、把三份 array_sum 收編——今天就做得到。

      兩個反例的完整循環

      • undefined-close：對結案(2)訂單執行 close() 落入未定義的 $updateData → replay 確認 PHP 層「Undefined variable」洩漏 → 裁定「冪等回傳」→ 修復 → replay 轉綠
      • illegal-transition：刪除銷貨單時 Controller 無條件把訂單蓋回 1 → replay 確認結案單被繞道重開、手動結案單被誤解除 → 裁定「設計對、實作錯」→ 收進 OrderService::reopen() 僅允許 2→1 → replay 轉綠

      教科書沒寫的兩個教訓

      • 狀態名會說謊：status 3 在資料表叫「取消」，但程式碼 getCloseAttribute() 把 [2,3] 都當已結案、UI 是「結案／取消結案」toggle——它實際是「手動結案（未出貨）」。依誤名把 3 裁定成終態會砍掉真功能。教訓：規格語意要從「程式如何使用」驗證，不能只看資料表標籤；最後以 migration 正名為「結案（未出貨）」。
      • 修復後要砍 invariant：Q1 裁定後 inv_closeDefined 變成永遠不會觸發的空轉檢查（vacuous green），依紀律連同 undefinedClose flag 一起移除，而不是留著假裝還在驗證。

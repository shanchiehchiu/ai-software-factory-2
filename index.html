AI Software Factory 2.0

從 Agentic Coding 到分級驗證的軟體工程

一核心結論

AI 正在讓「產生 code」的成本趨近於零。Software Factory 的瓶頸因此從「誰寫得快」轉為：

我們憑什麼相信 AI 產生的東西是對的？而且信到什麼程度？

下一階段的重點不是增加更多 Agent，而是建立分級驗證。每個產出物都要有與其風險相稱的證據：

Specification → Generation → Verification → Evidence → Release

這個主張有兩個前提。第一，驗證強度是一條光譜，不是「有證明 / 沒證明」的二選一。第二，驗證只能保證「產出符合規格」，規格本身是否正確，仍然需要人來把關。

Martin Kleppmann 在 2025 年的判斷是：Formal Verification 過去沒有普及，主因是人工撰寫 proof 的成本太高。如果 LLM 能大量產生 proof，再由 deterministic proof checker 判定，其經濟結構有可能改變。這是條件式的預測，目前仍需要實證。

二四個階段（並存，而非取代）

階段特徵主要限制
1. 傳統工程人設計、人寫、人審產能 ≈ 工程師數量 × 速度
2. AI CodingPrompt → AI 產碼 → 人審產碼速度超過審查與測試速度
3. Agentic Factory多 Agent 分工，有 sandbox、quality gate、audit evidence、approval gate驗證者與生成者同為機率模型
4. Verifiable Engineering關鍵產出物由確定性機制判定規格正確性、適用範圍、驗證成本

實務上這四個階段會同時存在。多數系統停在 Stage 3，只有高風險模組才導入 Stage 4。

三Multi-Agent 為何不能保證正確性

假設 Agent A 寫程式，B 審查，C 寫測試，D 做安全審查。四者都是機率模型，會有相關性失敗：共享訓練偏誤，可能一起接受同一個錯誤假設。

這能顯著提高品質，但沒有取得正確性保證。同樣的問題也出現在 AI 自己寫的測試：測試執行是確定性的，但測試案例只覆蓋 AI 想到的情境，這不等於正確性證明。

四驗證強度光譜

「Deterministic」不是單一概念。各層保證的強度與成本差異很大：

層級機制保證的內容典型適用
L0Lint、格式檢查風格一致全部程式碼
L1型別系統、靜態分析排除一整類錯誤全部程式碼
L2範例測試、整合測試已列舉情境成立全部功能
L3屬性測試、突變測試、契約測試較廣的輸入空間與測試品質核心業務邏輯、API 邊界
L4模型檢查有限狀態空間內窮舉狀態機、協定、併發
L5定理證明（Formal Proof）對規格的數學保證密碼學、金流核心、安全關鍵

原則是依風險選層級，不要一律追求 L5。L0 到 L2 的 AI 產出物已經可以大量自動化。越往上，成本越高，適用範圍越窄。

五規格才是新的瓶頸

Proof checker 只能回答「程式是否符合規格」，無法回答「規格是否符合使用者真正要的東西」。

  • 形式規格本身需要人撰寫，也可能寫錯。
  • 若讓 LLM 同時產生規格與證明，checker 只保證兩者互相一致。相關性失敗只是從程式層搬到規格層。
  • 多數業務系統（CRUD、報表、UI、第三方整合、權限規則）沒有現成的形式規格可寫。

因此流程中必須有一道人類主導的 Specification Review。它是獨立關卡，不能被 AI 的自我審查取代。

六確定性驗證層架構

Human: 寫作 / 審閱 Specification  ← 人類把關點
        ↓
AI: 生成 Artifact（code / test / proof）
        ↓
┌──────────────────────────────┐
│ 依風險分級的 Deterministic    │
│ Checker（L0 ~ L5）            │
└──────────────────────────────┘
        ↓
Pass / Fail ──Fail──→ 回到 AI 重試（有次數與成本上限）
        ↓ Pass
Evidence 封存 → Release Gate

分工是：AI 負責搜尋解法，機器負責判定，人負責定義「什麼叫對」。

七Evidence 的具體形態

「Evidence」必須是可稽核的實物，而不是一句「已驗證」：

  • 型別檢查與靜態分析報告
  • 測試結果、覆蓋率、突變測試分數（用來檢驗測試本身的品質）
  • 屬性測試的種子與反例紀錄
  • Proof artifact 與 checker 版本
  • 規格版本與人工審閱紀錄
  • 驗證所用工具鏈的版本與雜湊

八風險與未解問題

  1. 證明失敗時怎麼辦：LLM 反覆重試的成本需要預算上限，超過就轉人工或降級驗證層級。
  2. 證明通過但規格有漏洞：責任歸屬要事先定義，否則 Evidence 會製造虛假的安全感。
  3. 工具鏈的信任基礎：checker 與 kernel 本身必須小而可信，且版本鎖定。
  4. 適用範圍界線：每個專案應明確標示哪些模組在哪個驗證層級，不要用一句「已驗證」概括整個系統。
  5. 目前的證據不足：LLM 產生複雜 proof 的成功率與成本，仍待實測，不能當作已成立的趨勢。

九落地建議

  1. 全面做 L0 到 L2：型別、靜態分析、測試，由 AI 大量產出並自動把關。
  2. 對核心邏輯加 L3：導入屬性測試與突變測試，專門對付「AI 自己寫的測試太容易通過」。
  3. 挑 1 到 2 個高風險模組試 L4 或 L5，用實測數據評估成本，而不是先假設會成功。
  4. 建立 Specification Review 關卡，由人負責，並把規格版本納入 Evidence。
  5. 為每個模組標註驗證等級，讓 Release 決策建立在可見的證據上。

十一句話總結

AI 負責搜尋解法，機器依風險分級判定，人負責定義什麼叫對。
Software Factory 的競爭力不在於產得多，而在於每一份產出都附帶與其風險相稱的證據。
